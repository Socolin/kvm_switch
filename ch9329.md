The CH9329 chip has 3 serial communication modes:

- Serial communication mode 0: Protocol Transfer Mode (default)
- Serial communication mode 1: ASCII Mode
- Serial communication mode 2: Transparent Transfer Mode

The CH9329 chip works in serial communication mode 0 (Protocol Transfer Mode) by default. This protocol is mainly used to specify the serial communication protocol of the CH9329 chip operating in that mode.

In any mode, once the chip detects that the SET pin is at a low level, it automatically switches to "Protocol Transfer Mode", and the client serial device can perform parameter configuration. Therefore, when parameter configuration is needed, you can first set the SET pin low, then perform the configuration.

## 2. Communication Method

The communication between a peripheral serial device (PC, MCU, or other serial device) and the CH9329 chip is master-slave: the peripheral serial device is the master, and the CH9329 chip is the slave. All commands are initiated by the peripheral serial device, and the CH9329 chip responds passively. If the peripheral serial device does not receive a response from the CH9329 chip within 500 ms, or the response information is wrong, the communication is considered to have failed.

### 2.1 Frame Format Description

Communication is done in units of frames, i.e. sent in the form of data packets. Every frame of data carries a frame-header byte, an address code, a command code, a subsequent-data length, subsequent data, and a checksum (sum). If the CH9329 chip receives an erroneous frame, it returns an error-response frame or simply discards it.

In the following, the communication frame initiated by the peripheral serial device is called a **"command packet"**, and the communication frame returned by the CH9329 chip is called a **"response packet"**. For a "command packet", after the peripheral serial device sends it, it needs to wait for the CH9329 chip to return a "response packet", and use the "response packet" to determine whether this command executed successfully. If an error status is returned, or no "response packet" is received, then retry or handle the error according to the situation.

**Note: All data described below is in hexadecimal format.**

The command-packet and response-packet data format is as follows:

| Frame Header | Address | Command | Subsequent Data Length | Subsequent Data | Checksum |
|--------------|---------|---------|------------------------|-----------------|----------|
| HEAD | ADDR | CMD | LEN | DATA | SUM |
| 2 bytes | 1 byte | 1 byte | 1 byte (CH9329F supports extending to 2 bytes) | N bytes (0–64) (CH9329F supports extending to 0–512 bytes) | 1 byte |

**Frame Header (HEAD):** Occupies 2 bytes, fixed as `0x57`, `0xAB`.

**Address (ADDR):** Occupies 1 byte, defaults to `0x00`, which can receive command packets with any address code. If the chip address is set to `0x01`–`0xFE`, then it can only receive command packets with the matching address code or with address code `0xFF`. `0xFF` is a broadcast packet, and the chip does not need to respond to it.

**Command (CMD):** Occupies 1 byte. The valid range of command codes for frames initiated by the peripheral serial device is `0x01`–`0x3F`. When the CH9329 chip sends a normal response packet, the command code is: *original command code* `| 0x80`. When the CH9329 chip sends an abnormal (error) response packet, the command code is: *original command code* `| 0xC0`.

**Subsequent Data Length (LEN):** Occupies 1 byte, mainly used to record the actual length of the subsequent data in this packet. It only includes the subsequent-data part, and does not include the frame-header bytes, address code, command code, or checksum byte.

For the CH9329F chip: for the original commands, the subsequent-data length is still 1 byte, but the actual subsequent data can support 0–255 bytes. For the newly added extended commands, the subsequent-data length is extended to 2 bytes, and the actual subsequent data can support 0–512 bytes, high byte first — for example, for 500 bytes, the 2 length bytes are `0x01`, `0xF4`.

**Subsequent Data (DATA):** Occupies N bytes, with valid range N = 0–64.

For the CH9329F chip: for the original commands, the subsequent data can support 0–255 bytes. For the newly added extended commands, the subsequent data can support 0–512 bytes.

**Checksum (SUM):** Occupies 1 byte, calculated as: `SUM = HEAD + ADDR + CMD + LEN + DATA`.

### 2.2.1 CMD_GET_INFO

Get the version number, USB enumeration status, keyboard caps/indicator light status, and other information from the chip.

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x01 | 0x00 | No data | 0x03 |

This command carries no parameters.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x81 | 0x08 | 8 data bytes | 0x?? |

The 8 returned subsequent-data bytes are, in order:

1. **1 byte chip version number:** e.g. `0x30` = V1.0, `0x31` = V1.1.
2. **1 byte USB enumeration status:**
    - `0x00` = USB not connected to the computer, or not recognized.
    - `0x01` = USB connected to the computer and recognized successfully.
3. **1 byte current keyboard indicator-light status:**
    - Bit 0: NUM LOCK indicator status — 0 = off, 1 = on.
    - Bit 1: CAPS LOCK indicator status — 0 = off, 1 = on.
    - Bit 2: SCROLL LOCK indicator status — 0 = off, 1 = on.
    - Bits 7–3: Not used.
4. **1 byte current computer sleep status:**
    - `0x03` = computer is asleep; any other value = computer is not asleep.
5. **4 bytes reserved.**

### 2.2.2 CMD_SEND_KB_GENERAL_DATA

Send a general keyboard data packet to the chip to simulate a normal key press or release action. It supports full-keyboard and combination-key operations, with up to 8+6 non-conflicting keys, where 8 is the 8 control keys (Left Ctrl, Right Ctrl, Left Shift, Right Shift, Left Windows, Right Windows, Left Alt, and Right Alt), and 6 is the 6 ordinary keys other than the control keys.

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x02 | 8 | 8 data bytes | 0x?? |

This command carries 8 bytes of subsequent data, which are the key values of USB keyboard general keys. In order:

**(1) Byte 1:** 1 byte of control keys, each bit representing one key, as follows:

| BIT7 | BIT6 | BIT5 | BIT4 | BIT3 | BIT2 | BIT1 | BIT0 |
|------|------|------|------|------|------|------|------|
| Right Windows | Right Alt | Right Shift | Right Ctrl | Left Windows | Left Alt | Left Shift | Left Ctrl |

**(2) Byte 2:** 1 byte `0x00`; this byte must be `0x00`.

**(3) Bytes 3–8:** 6 bytes of general key values, representing up to 6 keys pressed. If no key is pressed, fill with `0x00`.

For the specific general keys and their key codes, see Appendix 1 – "CH9329 Key Code Table".

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x82 | 1 | 1 data byte | 0x?? |

The 1 returned subsequent-data byte is: the current command execution status.

**Examples:**

**Example 1:** To simulate pressing the "A" key and then releasing the "A" key, send 2 command packets:

1. Simulate pressing "A": `0x57, 0xAB, 0x00, 0x02, 0x08, 0x00, 0x00, 0x04, 0x00, 0x00, 0x00, 0x00, 0x00, 0x10`.
2. Simulate releasing "A": `0x57, 0xAB, 0x00, 0x02, 0x08, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x0C`.

**Example 2:** To simulate pressing "Left Shift" + "A" together, then releasing, send 2 command packets:

1. Simulate pressing "Left Shift" + "A": `0x57, 0xAB, 0x00, 0x02, 0x08, 0x02, 0x00, 0x04, 0x00, 0x00, 0x00, 0x00, 0x00, 0x12`.
2. Simulate releasing all keys: `0x57, 0xAB, 0x00, 0x02, 0x08, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x0C`.

### 2.2.4 CMD_SEND_MS_ABS_DATA

Send an absolute mouse data packet to the chip to simulate absolute mouse actions (including left/middle/right button press and release, scroll wheel up/down, and up/down/left/right movement).

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x04 | 7 | 7 data bytes | 0x?? |

This command carries 7 bytes of subsequent data, which form the USB absolute mouse data packet. In order:

**(1) Byte 1:** Must be `0x02`.

**(2) Byte 2:** 1 byte of mouse button values, where the lowest 3 bits each represent one button, as follows:

| BIT7 | BIT6 | BIT5 | BIT4 | BIT3 | BIT2 | BIT1 | BIT0 |
|------|------|------|------|------|------|------|------|
| 0 | 0 | 0 | 0 | 0 | Middle button | Right button | Left button |

BIT2–BIT0: 1 = the button is pressed; 0 = the button is released or not pressed.

**(3) Bytes 3–4:** 2 bytes of X-axis coordinate value, low byte first, high byte last.

**(4) Bytes 5–6:** 2 bytes of Y-axis coordinate value, low byte first, high byte last.

**(5) Byte 7:** 1 byte scroll-wheel scroll amount (in notches):
- If 0, no scroll action.
- `0x01`–`0x7F`: scroll up, unit: notches.
- `0x81`–`0xFF`: scroll down, unit: notches.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x84 | 1 | 1 data byte | 0x?? |

The 1 returned subsequent-data byte is: the current command execution status.

**Note:** The chip's default simulated absolute-mouse resolution is 4096 × 4096. When the peripheral serial device sends absolute XY values, it must first calculate them based on its own screen resolution, then send the calculated values.

For example, if the current screen resolution is X_MAX(1280) × Y_MAX(768), and you need to move to point (100, 120), perform the following calculation:

```
X_Cur = ( 4096 * 100 ) / X_MAX
Y_Cur = ( 4096 * 120 ) / Y_MAX
```

**Examples:**

**Example 1:** To simulate pressing the mouse "Left" button and then releasing it, send 2 command packets:

1. Press mouse "Left" button: `0x57, 0xAB, 0x00, 0x04, 0x07, 0x02, 0x01, 0x00, 0x00, 0x00, 0x00, 0x00, 0x10`.
2. Release mouse "Left" button: `0x57, 0xAB, 0x00, 0x04, 0x07, 0x02, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x0F`.

**Example 2:** Assume the screen resolution is 1280 × 768, and you want to move the mouse first to position (100, 100), then to position (968, 500). Send 2 command packets:

1. Move to (100, 100):
   ```
   X1 = ( 100 * 4096 ) / 1280 = 320 = 0x140
   Y1 = ( 100 * 4096 ) / 768  = 533 = 0x215
   ```
   Command packet: `0x57, 0xAB, 0x00, 0x04, 0x07, 0x02, 0x00, 0x40, 0x01, 0x15, 0x02, 0x00, 0x67`.

2. Move to (968, 500):
   ```
   X1 = ( 968 * 4096 ) / 1280 = 3097 = 0xC19
   Y1 = ( 500 * 4096 ) / 768  = 2667 = 0xA6B
   ```
   Command packet: `0x57, 0xAB, 0x00, 0x04, 0x07, 0x02, 0x00, 0x19, 0x0C, 0x6B, 0x0A, 0x00, 0xA9`.

### 2.2.5 CMD_SEND_MS_REL_DATA

Send a relative mouse data packet to the chip to simulate relative mouse actions (including left/middle/right button press and release, scroll wheel up/down, and up/down/left/right movement).

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x05 | 5 | 5 data bytes | 0x?? |

This command carries 5 bytes of subsequent data, which form the USB relative mouse data packet. In order:

**(1) Byte 1:** Must be `0x01`.

**(2) Byte 2:** 1 byte of mouse button values, where the lowest 3 bits each represent one button, as follows:

| BIT7 | BIT6 | BIT5 | BIT4 | BIT3 | BIT2 | BIT1 | BIT0 |
|------|------|------|------|------|------|------|------|
| 0 | 0 | 0 | 0 | 0 | Middle button | Right button | Left button |

BIT2–BIT0: 1 = the button is pressed; 0 = the button is released or not pressed.

**(3) Byte 3:** 1 byte X-direction movement distance:
- A. No move: byte 3 = `0x00`, no movement along the X-axis.
- B. Move right: `0x01 <= byte 3 <= 0x7F`; pixels moved = byte 3.
- C. Move left: `0x80 <= byte 3 <= 0xFF`; pixels moved = `0x00 - byte 3`.

**(4) Byte 4:** 1 byte Y-direction movement distance:
- A. No move: byte 4 = `0x00`, no movement along the Y-axis.
- B. Move right/down: `0x01 <= byte 4 <= 0x7F`; pixels moved = byte 4.
- C. Move left/up: `0x80 <= byte 4 <= 0xFF`; pixels moved = `0x00 - byte 4`.

**(5) Byte 5:** 1 byte scroll-wheel scroll amount (in notches):
- `0x01`–`0x7F`: screen scrolls up, unit: notches.
- `0x81`–`0xFF`: screen scrolls down, unit: notches.
- Distance calculation for scrolling down: e.g. if the byte is `0x81`, actual distance = `0x100 - 0x81` = 127 pixels; if the byte is `0xFF`, actual distance = `0x100 - 0xFF` = 1 pixel.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x85 | 1 | 1 data byte | 0x?? |

The 1 returned subsequent-data byte is: the current command execution status.

**Examples:**

**Example 1:** To simulate pressing the mouse "Left" button and then releasing it, send 2 command packets:

1. Press mouse "Left" button: `0x57, 0xAB, 0x00, 0x05, 0x05, 0x01, 0x01, 0x00, 0x00, 0x00, 0x0E`.
2. Release mouse "Left" button: `0x57, 0xAB, 0x00, 0x05, 0x05, 0x01, 0x00, 0x00, 0x00, 0x00, 0x0D`.

**Example 2:** To move the mouse first 3 pixels to the left, then 5 pixels down, send 2 command packets:

1. Move left 3 pixels: `0x57, 0xAB, 0x00, 0x05, 0x05, 0x01, 0x00, 0xFD, 0x00, 0x00, 0x0A`.
2. Move down 5 pixels: `0x57, 0xAB, 0x00, 0x05, 0x05, 0x01, 0x00, 0x00, 0x05, 0x00, 0x12`.

### 2.2.8 CMD_GET_PARA_CFG

Get the current parameter configuration information from the chip. See the returned-data description below for the specific parameters.

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x08 | 0 | None | 0x?? |

This command carries no parameter data.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x88 | 50 | 50 data bytes | 0x?? |

The 50 returned subsequent-data bytes are, in order:

**(1) 1 byte chip working mode:** Valid values `0x00`–`0x03`, `0x80`–`0x83`; default `0x80`.
- `0x00`: Software-set working mode 0 — standard USB keyboard (general + multimedia) + USB mouse (absolute + relative).
- `0x01`: Software-set working mode 1 — standard USB keyboard (general).
- `0x02`: Software-set working mode 2 — standard USB mouse (absolute + relative).
- `0x03`: Software-set working mode 3 — standard USB custom HID class device.
- `0x80`: Hardware-pin-set working mode 0 — standard USB keyboard (general + multimedia) + USB mouse (absolute + relative); current MODE1 pin high, MODE0 pin high.
- `0x81`: Hardware-pin-set working mode 1 — standard USB keyboard (general); current MODE1 pin high, MODE0 pin low.
- `0x82`: Hardware-pin-set working mode 2 — standard USB mouse (absolute + relative); current MODE1 pin low, MODE0 pin high.
- `0x83`: Hardware-pin-set working mode 3 — standard USB custom HID class device; current MODE1 pin low, MODE0 pin low.

**(2) 1 byte chip serial communication mode:** Valid values `0x00`–`0x02`, `0x80`–`0x82`; default `0x80`.
- `0x00`: Software-set serial communication mode 0 — Protocol Transfer Mode.
- `0x01`: Software-set serial communication mode 1 — ASCII Mode.
- `0x02`: Software-set serial communication mode 2 — Transparent Transfer Mode.
- `0x80`: Hardware-pin-set serial communication mode 0 — Protocol Transfer Mode; current CFG1 pin high, CFG0 pin high.
- `0x81`: Hardware-pin-set serial communication mode 1 — ASCII Mode; current CFG1 pin high, CFG0 pin low.
- `0x82`: Hardware-pin-set serial communication mode 2 — Transparent Transfer Mode; current CFG1 pin low, CFG0 pin high.

**(3) 1 byte chip serial communication address:** Valid range `0x00`–`0xFF`; default `0x00`.

**(4) 4 bytes chip serial communication baud rate:** High byte first; default `0x00002580`, i.e. baud rate 9600 bps.

**(5) 2 bytes reserved.**

**(6) 2 bytes chip serial communication packet interval:** Valid range `0x0000`–`0xFFFF`; default 3; unit ms. That is, if the chip does not receive the next byte within 3 ms, it treats this as the end of the packet.

**(7) 4 bytes chip USB VID and PID:** In working mode 0, the chip defaults to VID `0x1A86`, PID `0xE129` (CH9329) or `0xE12A` (CH9329F). The PID differs across working modes.

**(8) 2 bytes chip USB keyboard upload time interval (ASCII mode only):** Valid range `0x0000`–`0xFFFF`; default 0; unit ms. That is, the chip uploads the next packet immediately after finishing the previous packet.

**(9) 2 bytes chip USB keyboard release delay time (ASCII mode only):** Valid range `0x0000`–`0xFFFF`; default 1; unit ms. That is, 1 ms after uploading the key-press data packet, the chip uploads the key-release data packet.

**(10) 1 byte chip USB keyboard auto-enter flag (ASCII mode only):** Valid range `0x00`–`0x01`. `0x00` = do not auto-enter; `0x01` = auto-enter after this packet ends.

**(11) 8 bytes chip USB keyboard enter (carriage return) characters (ASCII mode only):** 4 bytes per group, 2 groups total, i.e. you can set 2 different enter characters. By default, an enter is performed when the ASCII value `0x0D` is encountered.

**(12) 8 bytes chip USB keyboard filter start/end strings:** The first 4 bytes are the filter start characters, and the last 4 bytes are the filter end characters.

**(13) 1 byte chip USB string enable flag:**
- Bit 7: 0 = disable; 1 = enable custom string descriptor.
- Bits 6–3: reserved.
- Bit 2: 0 = disable; 1 = enable custom manufacturer string descriptor.
- Bit 1: 0 = disable; 1 = enable custom product string descriptor.
- Bit 0: 0 = disable; 1 = enable custom serial-number string descriptor.

**(14) 1 byte chip USB keyboard fast-upload flag (ASCII mode only):** Valid range `0x00`–`0x01`. `0x00` = normal USB keyboard upload speed; `0x01` = enable USB keyboard fast-upload mode. After fast-upload mode is enabled, once a character is uploaded, the release-key packet is not sent — the next character continues to be uploaded, and only after all characters are uploaded is the release-key packet sent.

**(15) 12 bytes reserved:**
- For the CH9329, these 12 bytes are reserved.
- For the CH9329F chip, these 12 bytes function as follows:
    - **(a) 1 byte chip sleep-disable flag:** If it is the special value `0xFA`, the chip is set to disable sleep; any other value allows the chip to sleep/suspend. Default `0x00`.
    - **(b) 1 byte chip USB interface speed setting flag:** If it is the special value `0xFA`, the chip's USB is forced to operate in full-speed mode; any other value operates in high-speed mode. Default `0x00`.
    - **(c) 1 byte chip USB touchscreen mode enable flag:** If it is the special value `0xFA`, USB touchscreen mode is enabled, converting the USB absolute mouse into touchscreen mode; any other value applies no special handling. Default `0x00`.

### 2.2.16 CMD_GPIO_CONTROL

Send a GPIO control command to the chip to control GPIO as input/output pins. This command is a CH9329F chip extended command.

**Peripheral serial device → chip:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x12 | 1 byte | 3 data bytes | 0x?? |

This command carries N bytes of subsequent data, in order:

**(1) 1 byte GPIO operation sub-command word:**
- `0x00` = read the current GPIO status.
- `0x01` = set GPIO enable.
- `0x02` = set GPIO direction.
- `0x03` = set GPIO output level.

**(2) 2 bytes GPIO operation parameters:**
- BIT4–BIT0 correspond to the operation bits of GPIO4–0 respectively.
    - **(a) When the sub-command is `0x00`,** these 2 bytes are invalid.
    - **(b) When the sub-command is `0x01`,** the 1st byte is used to set GPIO enable (BIT4–0 valid); 1 = enable the corresponding pin. The 2nd byte is whether GPIO input status is auto-reported: `0x00` = do not auto-report; `0x01` = auto-report. After the auto-report function is enabled, if a change in the input GPIO pin is detected, a response packet is automatically returned, automatically uploading the status to the peripheral serial master.
    - **(c) When the sub-command is `0x02`,** the 1st byte indicates whether the corresponding GPIO needs a direction setting this time (BIT4–0 valid); 1 = set the direction of the corresponding pin this time. The 2nd byte indicates the direction of the corresponding GPIO this time; 1 = set as output, 0 = set as input.
        - E.g. `0x01` and `0x01`: this operation sets GPIO0 direction as output.
        - E.g. `0x07` and `0x07`: this operation sets GPIO0, GPIO1, and GPIO2 direction as output.
    - **(d) When the sub-command is `0x03`,** the 1st byte indicates whether the corresponding GPIO needs an output setting this time (BIT5–0 valid); 1 = control the high/low output level of the corresponding pin this time. The 2nd byte indicates the high/low output level to control this time; 1 = output high level, 0 = output low level.
        - E.g. `0x01` and `0x01`: this controls GPIO0 to output high level.
        - E.g. `0x07` and `0x01`: this controls GPIO0 to output high level, and GPIO1 and GPIO2 to output low level.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0x92 | 1 byte | 4 data bytes | 0x?? |

The returned subsequent data (listed as 3 bytes) is, in order:

1. **1 byte GPIO operation sub-command word.**
2. **1 byte current GPIO real-time status.**
3. **1 byte current GPIO enable status.**
4. **1 byte current GPIO direction setting status.**

## 2.3 Error Response Packet

If a command packet received by the chip has a problem such as a command-code error, checksum error, or execution failure, it must respond with an error response packet. An error response packet contains 1 byte of subsequent data, which is the command execution status.

**Chip → peripheral serial device:**

| HEAD | ADDR | CMD | LEN | DATA | SUM |
|------|------|-----|-----|------|-----|
| 0x57, 0xAB | 0x00 | 0xC? | 1 | 1 data byte | 0x?? |

The 1 returned subsequent-data byte is: the current command execution status.

Returned command code = *original command code* `| 0xC0`.

**Table 2 – Command Execution Status**

| Status Name | Status Code | Status Description |
|-------------|-------------|--------------------|
| DEF_CMD_SUCCESS | 0x00 | Command executed successfully |
| DEF_CMD_ERR_TIMEOUT | 0xE1 | Serial port timed out receiving a byte |
| DEF_CMD_ERR_HEAD | 0xE2 | Serial port received an erroneous packet-header byte |
| DEF_CMD_ERR_CMD | 0xE3 | Serial port received an erroneous command code |
| DEF_CMD_ERR_SUM | 0xE4 | Checksum value mismatch |
| DEF_CMD_ERR_PARA | 0xE5 | Parameter error |
| DEF_CMD_ERR_OPERATE | 0xE6 | Frame normal, but execution failed |
